# Feature Specification: 认证功能整合进实时服务

**Feature Branch**: `004-integrate-auth-server`

**Created**: 2026-08-04

**Status**: Draft

**Input**: 用户描述："rtmate-auth 的功能整合到 rtmate-server 中"

## Clarifications

### Session 2026-08-04

- **Q**：如何量化“统一数据库查询与统一返回参数”？
  - **A**：所有数据库访问集中在统一的 repository 层；认证与实时功能共享同一连接池与事务/错误模式；handler/service 层不直接执行 SQL；所有对外响应统一使用项目通用的响应封套，handler 不返回裸类型或自定义 JSON。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 单一服务同时提供认证与实时通信 (Priority: P1)

作为部署运维方，我只部署并运行一个 RTMate 服务进程，即可同时获得"应用认证签发令牌"与"WebSocket 实时发布/订阅"两项能力，无需再单独部署、配置和监控一个独立的认证服务。

**Why this priority**: 这是本特性的核心目标。当前认证能力存在于独立的 rtmate-auth 服务中，部署方需要维护两套进程、两套配置、两套日志，而两者共享同一份数据库与协议契约。合并后部署单元从 2 个降为 1 个，直接降低运维复杂度。

**Independent Test**: 启动合并后的服务进程，先用应用凭证通过认证接口获取令牌，再使用该令牌建立 WebSocket 连接并完成鉴权，验证全流程在单一进程内完成。

**Acceptance Scenarios**:

1. **Given** 只启动了一个 RTMate 服务进程，**When** 部署方检查该进程暴露的接口，**Then** 认证令牌签发接口与 WebSocket 实时接口均可用。
2. **Given** 服务已启动，**When** 客户端先获取令牌再凭令牌建立 WebSocket 连接，**Then** 两个环节均成功，且全程只与一个服务地址交互。

---

### User Story 2 - 客户端认证方式保持兼容 (Priority: P2)

作为应用客户端开发者，我继续使用现有的认证方式（应用标识 + 随机状态 + 时间戳 + 签名）请求令牌，获得的令牌格式、字段与错误响应与整合前完全一致，无需修改任何客户端代码。

**Why this priority**: 整合是对服务端部署形态的重构，绝不能破坏既有客户端。协议兼容是该重构成立的前提，优先级仅次于"整合成功"本身。

**Independent Test**: 用整合前的客户端请求样例分别请求整合后的认证接口，对比成功响应的令牌结构与各失败场景（应用不存在、签名不匹配）的错误码和错误信息，确认与整合前一致。

**Acceptance Scenarios**:

1. **Given** 一个持有合法应用凭证的客户端，**When** 按原有协议请求令牌，**Then** 获得与整合前结构一致的访问令牌与连接令牌。
2. **Given** 一个签名不正确的请求，**When** 请求令牌，**Then** 返回与整合前相同的"签名无效"错误。
3. **Given** 一个使用未注册应用标识的请求，**When** 请求令牌，**Then** 返回与整合前相同的"应用未找到"错误。

---

### User Story 3 - 代码库移除独立认证模块 (Priority: P3)

作为项目维护者，整合完成后代码库中不再存在独立的认证模块/包，认证逻辑成为实时服务的一部分；共享的数据模型、错误类型与协议契约仍然只有一份定义，整个项目一次构建、一次测试即可全部通过。

**Why this priority**: 这是整合的收尾与长期收益：消除重复配置、重复依赖与跨模块私有耦合风险。但它依赖于前两个故事先保证功能与协议无损，因此排为 P3。

**Independent Test**: 检查项目结构中不再包含独立认证模块，执行全量构建与测试，确认全部通过且无残留引用。

**Acceptance Scenarios**:

1. **Given** 整合完成后的代码库，**When** 执行全量构建，**Then** 构建成功且不再产出独立认证服务的可执行文件。
2. **Given** 整合完成后的代码库，**When** 执行全量测试与静态检查，**Then** 全部通过。

---

### Edge Cases

- 认证接口所需的数据库不可用时，错误响应格式与整合前保持一致，且不影响 WebSocket 接口已有连接的正常通信。
- 配置缺失（如数据库连接串、密钥配置）时，服务启动应给出明确的错误提示而非静默失败。
- 整合后同一进程内认证流量与实时消息流量并存时，任一方的高负载不得导致另一方整体不可用。
- 历史签发的未过期令牌在整合后的服务上仍可正常用于 WebSocket 鉴权。
- 迁移过程中不得出现两套数据库访问实现并存：所有新增或保留的 SQL 操作必须归入统一 repository 模块；任何 handler 返回的响应必须能被统一响应封套覆盖。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在单一服务进程内同时提供"应用认证令牌签发"接口与 WebSocket 实时通信接口。
- **FR-002**: 系统 MUST 保持认证请求协议不变：客户端仍以应用标识、随机状态、时间戳与签名请求令牌。
- **FR-003**: 系统 MUST 保持认证响应协议不变：成功时返回的令牌结构与内容、失败时返回的错误码与错误信息均与整合前一致。
- **FR-004**: 系统 MUST 保持 WebSocket 端既有的鉴权、订阅、发布与广播行为不变。
- **FR-005**: 认证功能与实时功能 MUST 共享同一份配置来源与数据库连接，不再要求分别为两个服务维护配置。
- **FR-006**: 整合后的代码库 MUST 不再包含独立的认证服务模块/包，认证逻辑并入实时服务。
- **FR-007**: 整合后 MUST 只保留一份共享数据模型、错误类型与协议契约的定义，不产生重复拷贝。
- **FR-008**: 整合后的服务 MUST 对认证与连接生命周期保持结构化日志记录，且日志不泄露密钥与完整令牌。
- **FR-009**: 整合后项目文档 MUST 更新，移除"独立认证服务"的描述，反映单一服务的部署形态。
- **FR-010**: 整合后认证与实时功能的数据库访问 MUST 统一在同一 repository 层；handler/service 层不得直接执行 SQL；共享同一连接池与事务/错误处理模式。
- **FR-011**: 整合后所有 HTTP/WebSocket 对外响应 MUST 统一使用项目通用的响应封套，handler 不得返回裸领域类型或自定义 JSON 结构。

### Key Entities *(include if feature involves data)*

- **应用（RtApp）**: 已注册的应用方，持有应用标识与应用密钥，是认证签名校验的依据。
- **认证令牌（Token）**: 认证成功后签发的访问凭证，用于后续 WebSocket 连接鉴权。
- **客户端连接（RtClientConnection）**: 认证成功后登记的连接记录，关联应用与客户端标识。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 部署方只需启动 1 个服务进程、维护 1 份配置，即可完成"获取令牌 → 建立 WebSocket 连接 → 发布/订阅"全流程。
- **SC-002**: 整合前编写的客户端集成代码在不做任何修改的情况下，100% 能完成认证与连接。
- **SC-003**: 认证接口在成功、签名无效、应用未找到三类场景下的响应，与整合前逐字段一致。
- **SC-004**: 项目全量构建、全量测试与静态检查 100% 通过，且无对已移除认证模块的残留引用。
- **SC-005**: 部署文档中的启动步骤较整合前减少（从分别启动两个服务简化为启动一个服务）。
- **SC-006**: 整合后的代码中，所有数据库访问必须经由统一 repository 层，且所有 HTTP/WebSocket handler 必须通过统一响应封套返回结果；代码评审中未发现 handler/service 直接执行 SQL 或返回裸 JSON 的情况。

## Assumptions

- 独立部署认证服务的形态不再需要保留；认证仅作为实时服务的一个接口存在。
- 对外认证接口的路径、请求/响应协议与数据库表结构保持不变，本次整合不引入协议或数据模型的变更。
- 整合前的令牌签发与校验逻辑视为正确实现，整合以"原样迁移、不改行为"为原则。
- 两个服务当前共享同一个数据库，整合后继续沿用该数据库，无需数据迁移。
- 客户端与运维方均能接受服务重启带来的短暂中断（整合发布属于一次正常的版本发布）。
- 整合后的数据库访问层以"统一 repository 层"为目标；原 `rtmate-auth` 的 repository 实现迁移后应与 `rtmate-server` 的 repository 目录、命名与错误模式保持一致，而非直接复制到 handler 旁。
